# Support Ticket Management System — Data Model

**Status:** proposed logical/physical model, not implemented  
**Sources:** `spec/requirements.md`, `spec/architecture.md`  
**Constraint:** this document defines stored data, constraints, and rule placement only. It does not contain JPA entities, SQL migrations, or application code.

Where the written requirements do not decide a field, this model **names a seam** and marks it **unresolved**. Proposed defaults below are for schema design discussion; they are not silent product sign-off.

**Target store:** PostgreSQL (production/local). **Test store:** H2. Prefer portable types (`uuid`/`bigint`, `varchar`, `text`, `timestamp with time zone`) so the same conceptual schema can be applied in both.

---

## 1. Entity overview

Required by the product and architecture:

| Entity | Persistence | Role |
| --- | --- | --- |
| **Ticket** | table `ticket` | Aggregate root: identity, fields, current status |
| **Comment** | table `comment` | Child of a ticket; added over time |

Assignee is **not** specified as its own entity in the requirements. This model treats assignee as an **attribute of Ticket** until a User/directory entity is confirmed.

```
ticket 1 ──< comment
ticket.assignee  (scalar; User table unresolved)
```

## 2. Ticket

**Table:** `ticket`

### 2.1 Fields

| Field | Data type (PostgreSQL) | Required | Generated | Description |
| --- | --- | --- | --- | --- |
| `id` | **Unresolved** — see §7.1 | yes | yes | Primary key. Surrogate identifier. |
| `title` | `varchar(n)` — **n unresolved** | yes (proposed) | no | Short label. Create and update use cases. |
| `description` | `text` | **unresolved** required vs optional | no | Body of the ticket. |
| `priority` | `varchar(32)` storing an enum label | **unresolved** required vs optional | no | One of the allowed priority values (§5). |
| `status` | `varchar(32)` storing an enum label | yes | yes on insert (default `OPEN`) | Current lifecycle state. **Not** client-writable on field update. |
| `assignee` | **unresolved representation** — see §4 | **unresolved** | no | Who the ticket is assigned to; may be null if unassigned is allowed. |
| `created_at` | `timestamptz` | yes | yes | Insert time, UTC. |
| `updated_at` | `timestamptz` | yes | yes | Last successful mutation of the ticket row. |
| `version` | `bigint` | yes if optimistic locking is confirmed | yes | Optimistic lock column. **Architecture recommendation; not confirmed.** |

Display ticket ID (for example `TCK-0001`) is **not** assumed. If a human-readable code is required, it is a separate field from `id` (§7.1).

### 2.2 Constraints (ticket)

| Constraint | Kind | Purpose |
| --- | --- | --- |
| Primary key on `id` | database | Uniqueness and identity |
| `title` not null, non-blank | database not null + application trim/blank check | Empty titles should not persist. Blank-vs-whitespace is application logic. |
| `title` max length | database `varchar(n)` **and** API validation | **n unresolved** |
| `description` max length | application (and optional `check char_length`) | **limit unresolved**; `text` has no useful default max |
| `status` not null | database | Every ticket has a status |
| `status` in allowed set | database check or SQL enum | Value integrity only |
| `status` default `OPEN` | database default **or** application on create | Create path must not accept an arbitrary initial status from the client |
| `priority` in allowed set when not null | database check | Value integrity; whether null is allowed is **unresolved** |
| `created_at` / `updated_at` not null | database | Audit timestamps |
| `updated_at >= created_at` | optional check | Cheap consistency |
| No foreign key for assignee yet | — | No User table unless confirmed |

### 2.3 Relationships

- One ticket has many comments (`comment.ticket_id` → `ticket.id`).  
- Deleting a ticket: **unresolved** (restrict vs cascade). Architecture assumes comments belong to the ticket; cascade-on-delete is a reasonable default **if** tickets may be deleted. The requirements do not define ticket deletion.

### 2.4 Indexes (ticket)

| Index | Columns | Reason |
| --- | --- | --- |
| PK | `id` | Lookup by id (view/update/transition/comment) |
| `idx_ticket_status` | `status` | Filter tickets by status |
| `idx_ticket_created_at` | `created_at DESC` (proposed) | List ordering if newest-first is chosen |
| Search index | title/description | **Unresolved** — depends on search semantics (exact vs partial, case sensitivity). Options: btree on `title`, `pg_trgm` GIN, or full-text `tsvector`. H2 will not match Postgres full-text; keep search SQL portable or accept test/prod divergence. |
| `idx_ticket_assignee` | `assignee` | Only if filtering by assignee is added later (not in current requirements) |

### 2.5 Timestamps and generated identifiers (ticket)

- `id`: generated by the database (UUID or identity sequence — unresolved).  
- `created_at`: set once on insert (database `now()` at UTC or application clock; pick one and use it consistently).  
- `updated_at`: set on every row update (application or database trigger).  
- `status`: generated default `OPEN` on create; thereafter only the domain transition operation changes it.  
- `version`: incremented on update if optimistic locking is confirmed.

## 3. Comment

**Table:** `comment`

### 3.1 Fields

| Field | Data type (PostgreSQL) | Required | Generated | Description |
| --- | --- | --- | --- | --- |
| `id` | same strategy as ticket `id` (unresolved type) | yes | yes | Primary key. |
| `ticket_id` | same type as `ticket.id` | yes | no | Parent ticket. |
| `body` | `text` | yes (proposed) | no | Comment text. Max length **unresolved**. |
| `author` | **unresolved** — see §4 | **unresolved** | no | Who wrote the comment. Requirements do not define identity. |
| `created_at` | `timestamptz` | yes | yes | Insert time, UTC. |
| `updated_at` | `timestamptz` | only if comments are editable | yes | **Unresolved:** comments are add-only in the written requirements. |

No `status` on comments.

### 3.2 Constraints (comment)

| Constraint | Kind | Purpose |
| --- | --- | --- |
| Primary key on `id` | database | Identity |
| `ticket_id` not null | database | Comment always belongs to a ticket |
| Foreign key `ticket_id` → `ticket.id` | database | Referential integrity |
| `body` not null, non-blank | database not null + application blank check | Empty comments should be rejected |
| `body` max length | application / optional check | **limit unresolved** |
| `created_at` not null | database | Audit |

### 3.3 Relationships

- Many comments to one ticket.  
- Comments are not shared across tickets.  
- Edit/delete of comments is **not** in the requirements; the model does not add soft-delete or `edited` flags unless that product rule is decided.

### 3.4 Indexes (comment)

| Index | Columns | Reason |
| --- | --- | --- |
| PK | `id` | Identity |
| `idx_comment_ticket_id` | `ticket_id` | Load comments for ticket details |
| `idx_comment_ticket_created` | `(ticket_id, created_at)` | Stable chronological display |

### 3.5 Timestamps and generated identifiers (comment)

- `id`: generated surrogate.  
- `created_at`: set on insert.  
- No independent lifecycle timestamps unless edit/delete is confirmed.

## 4. Assignee representation

**Requirements:** tickets can be created, and assignee can be updated. There is no User, Agent, or directory requirement.

### 4.1 Proposed seam (pending confirmation)

Until a User entity exists, store assignee on `ticket` as a **nullable scalar**:

| Option | Column | Meaning |
| --- | --- | --- |
| **A. Display name / handle (proposed default for v1 schema discussion)** | `assignee varchar(n) NULL` | Free-text identifier. No FK. Unassigned = `NULL`. |
| B. Opaque user id without a users table | `assignee_id uuid NULL` | Implies an external identity system not in this spec. |
| C. First-class `users` table | `assignee_id` FK → `users.id` | Requires user lifecycle, uniqueness of email, etc. **Not in requirements.** |

Comment `author` is a **separate** decision. It may or may not use the same representation as assignee.

### 4.2 Constraints if option A is chosen

- `NULL` allowed **only if** unassigned tickets are allowed (**unresolved**).  
- If unassigned is forbidden: `assignee` not null, and create/update must supply a non-blank value (application + database).  
- Database **cannot** prove the assignee “already exists” without a User table. Existence checks would be application/integration logic.

### 4.3 Relationships

- Option A/B: no relationship table.  
- Option C: `ticket.assignee_id` many-to-one `users`. Comment author might similarly FK to `users`.

### 4.4 Indexes

- None required for current list/search/filter-by-status use cases.  
- Index `assignee` only if filtering or uniqueness of assignment becomes a requirement.

## 5. Valid status values

Taken from the written state machine. These **are** specified.

| Value | Allowed as stored current status | Initial value on create |
| --- | --- | --- |
| `OPEN` | yes | yes (only initial) |
| `IN_PROGRESS` | yes | no |
| `RESOLVED` | yes | no |
| `CLOSED` | yes | no |
| `CANCELLED` | yes | no |

Database: restrict `ticket.status` to this closed set (`CHECK (status IN (...))` or a Postgres enum type). H2 should use an equivalent check; avoid Postgres-only enum if it complicates tests.

**Not a database constraint:** which *next* status is legal. That is the transition policy in application/domain logic (`OPEN → IN_PROGRESS → RESOLVED → CLOSED`, `OPEN → CANCELLED`, `IN_PROGRESS → CANCELLED`). Unspecified edges are forbidden until explicitly added.

## 6. Valid priority values

**Not specified in requirements.** The following set is a **proposal for confirmation only**, not an adopted product rule:

| Proposed value | Intent |
| --- | --- |
| `LOW` | Least urgent |
| `MEDIUM` | Default candidate **if** a default is wanted (also unresolved) |
| `HIGH` | Urgent |
| `CRITICAL` | Highest |

If this set is rejected, the column type stays the same; only the check-constraint list and API enum change.

Database (after confirmation): `CHECK (priority IN (...))` and nullability per the required/optional decision.

## 7. Database constraints vs application / business logic

### 7.1 Belong in the database

Integrity that must hold even if a buggy writer or a future admin script touches rows:

- Primary keys and unique identifiers  
- Foreign key `comment.ticket_id` → `ticket.id`  
- `NOT NULL` on keys, `status`, timestamps  
- Closed set of **status labels**  
- Closed set of **priority labels** (once chosen)  
- Reasonable `varchar` length caps once chosen  
- Optional: `ticket.version` for optimistic locking  

These are **value and referential** constraints, not workflow.

### 7.2 Must remain in application / domain logic

- **Status transitions** (allowed pairs, rejection of `CLOSED → OPEN`, etc.)  
- Splitting “update fields” vs “transition status” (API must not persist a client-supplied status on PATCH/PUT)  
- Initial status is always `OPEN` even if a client sends another value  
- Search semantics (case, partial vs exact, which fields)  
- Status filter combination with search  
- Pagination and sorting  
- Blank/whitespace titles and comment bodies (beyond `NOT NULL`)  
- Cross-field product rules not yet specified  
- “Assignee must already exist” unless/until a `users` table and FK exist  
- Comment author identity and any authn/authz  
- Meaningful error payloads and HTTP mapping  

A database **trigger** that copies the transition table is optional defense in depth (`spec/architecture.md` §10). It is **not** the system of record for the rule and is **unresolved**. H2 trigger parity is a further cost.

### 7.3 Split rules (both layers)

| Rule | Database | Application |
| --- | --- | --- |
| Status is one of five labels | CHECK/enum | Same enum in API/domain |
| Status change is a legal edge | No (unless optional trigger) | Domain `transitionTo` |
| Title present | NOT NULL | Required on create/update; trim |
| Ticket has comments | FK | Load on details; reject comment if ticket missing (404) |
| Unassigned ticket | NULL allowed or not | Create/update validation |

## 8. Identifier generation

| Decision | Options | Notes |
| --- | --- | --- |
| Surrogate type | UUID vs `bigint` identity | Unresolved. UUID avoids guessable sequences; `bigint` is simpler in H2/Postgres. |
| Who generates | Database vs application | Prefer database default for `id`, `created_at`. |
| Public API id | Same as PK vs separate `ticket_number` | Unresolved. Requirements say nothing about format (`TCK-001` vs UUID). |
| Comment ids | Independent from ticket ids | Comments should not reuse ticket id sequences in a way that collides across tables if using UUIDs this is automatic. |

---

## 9. Timestamp representation

**Proposed (architecture recommendation, not product-confirmed):** store `timestamptz` in UTC; API serializes ISO-8601 instants (`2026-09-24T12:30:00Z`).

**Unresolved:** timezone of display in the UI, whether `updated_at` changes on comment-add (ticket row vs comment row only).

## 10. Unresolved data-model decisions

Product / schema decisions that **must** be confirmed before migrations or entities:

1. **Ticket `id` type and format** — UUID vs sequence vs separate display code.  
2. **Title required?** Max length?  
3. **Description required?** Max length?  
4. **Priority required?** Allowed values? Default on create?  
5. **Assignee representation** — free-text vs id vs `users` table.  
6. **Unassigned tickets allowed?** (`NULL` vs not null).  
7. **Must assignee already exist?** (only enforceable with a User/FK or an external directory).  
8. **Comment `body` max length.**  
9. **Comment author representation** — omitted, free-text, same as assignee, or authenticated user.  
10. **Comment mutability** — add-only vs edit/delete; whether `updated_at` exists; soft delete.  
11. **Ticket deletion** and comment FK `ON DELETE` behavior.  
12. **Optimistic locking `version` column** — include or omit.  
13. **Search support in schema** — extra indexes / `tsvector` vs simple `LIKE`.  
14. **Default list sort** — drives `created_at` / `updated_at` indexes.  
15. **Initial status default implemented in DB vs only in domain.**  
16. **Postgres ENUM type vs VARCHAR + CHECK** (H2 portability).  
17. **Optional transition trigger** in the database.  
18. **Clock source** — DB `now()` vs application clock for tests.  
19. **Whether adding a comment updates `ticket.updated_at`.**  
20. **Auth model** — if users exist, assignee/author likely become FKs and this document’s scalar assignee is replaced.

None of the items above should be inferred from this file as approved product behavior. Status **labels** and the **transition graph** are the only lifecycle facts taken as given from `spec/requirements.md`.
